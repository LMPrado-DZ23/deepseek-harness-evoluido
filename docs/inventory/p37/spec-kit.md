- rede_filesystem_segredos: rede — a CLI baixa templates de release do próprio repositório pelo GitHub e o README instrui instalar com `uv tool install ... --from git+https://github.com/github/spec-kit.git@vX.Y.Z`, isto é, o vetor de confiança é o GitHub e a tag escolhida; filesystem — `specify init` escreve a estrutura de projeto, templates e comandos de agente dentro do diretório de trabalho do usuário, e os comandos `/speckit-*` são instruções que o AGENTE executa, com o poder que o agente já tiver sobre o disco; segredos — o projeto em si não pede chave de API, mas o fluxo inteiro pressupõe um agente de código com credencial de provedor já configurada, e o conteúdo do repositório aberto vai como prompt para esse provedor. Não há script `preinstall`/`postinstall` (não há `package.json`), o que remove um vetor clássico de cadeia de suprimentos
- cves_conhecidas: NAO_VERIFICADO — motivo: nenhuma consulta a base de advisory foi possível nesta sessão, porque a API do GitHub responde HTTP 403 ("GitHub access to this repository is not enabled for this session") para qualquer repositório, inclusive públicos; o clone por HTTPS funciona, a API não. Registrado como lacuna a fechar antes de qualquer consumo real, e não como ausência de risco: projeto de um ano, 1.0.0 recente, ausência de CVE localizada é evidência fraca
- sbom: o projeto não publica SBOM oficial (nada encontrado na raiz do clone). Um SBOM é gerável a partir do `pyproject.toml` se e quando houver decisão de consumo — hoje não há, e como nada foi copiado não existe SBOM nosso a produzir por causa deste projeto
- sast: não executado — motivo objetivo: nenhum arquivo deste projeto está na árvore do produto, então não há nada sob alcance dos nossos scanners; rodar SAST em código de terceiro que não vamos consumir seria número sem consequência
- poc_isolado: nenhum PoC executado.
